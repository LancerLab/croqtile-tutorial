\subsection*{Swizzle and layout conflicts}

A swizzle changes how elements of a staged tile are arranged in shared storage. The logical matrix shape stays the same, but the reader must use the matching address mapping. Croqtile exposes this choice on both DMA and TMA copies:

\begin{lstlisting}[language=croqtile,caption={A swizzled copy}]
dma.copy.swiz<3> src => dst;       // software DMA with swizzle
tma.copy.swiz<3> src => dst;
\end{lstlisting}

The MMA read path must use the same \texttt{swiz\textless{}N\textgreater{}} so addresses match the staged layout:

\begin{lstlisting}[language=croqtile,caption={A swizzled mma load}]
ma = mma.load.swiz<3> lhs_load_s.chunkat(_, iv_warp);
\end{lstlisting}

Swizzle is not a TMA-specific feature. In Croqtile, \texttt{dma.\allowbreak{}copy.\allowbreak{}swiz\textless{}N\textgreater{}} and \texttt{tma.\allowbreak{}copy.\allowbreak{}swiz\textless{}N\textgreater{}} produce identical shared-memory layouts. The difference is only in how the data gets there; the layout that arrives is the same in both cases.

The template argument selects a target-supported swizzle mode. The examples use numbered modes, including mode 0 for the identity mapping. Valid modes and compatible tile extents depend on the target; use the same documented convention on the transfer and MMA load.

The copy and \co@mma.load.swiz<N>@ must agree on the layout. Loading a swizzled tile with an incompatible mode interprets the same bytes at different matrix positions, producing incorrect values. Treat this pairing as a correctness requirement when changing either operation.
