Consider what happens when a computation needs a different tile size. In a program where tiling, copying and coordination are written separately, that one change reaches into the loop bounds, the address arithmetic, the staging buffers and the coordination points. In Croqtile the iteration declares the tile, the tile selects the data, and a movement statement says when it is ready; the change stays local, and the compiler rejects the combinations that do not fit. That is the key benefit of making tiles part of the language: the person writing the program keeps the decisions, while the compiler takes on the bookkeeping that used to tie them together. It also means a complete kernel is short enough to read in one sitting, which is how the examples here are built.

The vocabulary follows the way a kernel is put together. A \co@__co__@ function describes the parallel work and sits beside the ordinary C++ that prepares buffers through the host API. Shaped types built on MDSpan and spanned data carry symbolic dimensions that need not be fixed until the program runs. Iteration constructs declare independent regions and loop over tiles, DMA statements and \texttt{chunkat} select and move those tiles, and events order the regions that share them. Where plain C++ is needed again, \co@__cpp__@ blocks, macros and the preprocessor are available in the same file. Appendix~\ref{app:quickref} collects the exact spelling of each form, and the chapters that follow put them to work in complete programs.
